# Production PostgreSQL Requirements — Phase 16

What a real production Postgres deployment for VerdictVaut must satisfy.
This is a requirements checklist, not a claim that any of it is
provisioned — no managed provider, cloud account, or persistent
production/staging database exists anywhere in this repository's
history (see `docs/database-backup-recovery.md` §1, unchanged by this
phase). Everything here is **READY FOR IMPLEMENTATION**, not verified
against a live production instance, unless a section says otherwise.

## 1. Version

**PostgreSQL 16+.** `infra/docker-compose.yml`'s local dev instance
already uses `postgres:16-alpine`; the schema uses no version-specific
extension or syntax beyond what any supported Postgres 16 install
provides. No Postgres extension (`pgcrypto`, `uuid-ossp`, etc.) is
required — every `@id @default(uuid())` in `prisma/schema.prisma` is
generated by Prisma's own query engine at write time, not a database
function.

## 2. TLS — enforced fail-closed, not optional

`src/config/database-tls.validator.ts`'s `assertDatabaseTlsConfigured`
requires `DATABASE_URL` to carry `sslmode=require`, `verify-ca`, or
`verify-full` whenever `APP_ENVIRONMENT=production` — checked at boot
by both `env.validation.ts` (currently unreachable in practice, since
`APP_ENVIRONMENT=production` is refused outright for other reasons —
see `docs/deployment-architecture.md` §5) and independently by
`scripts/production-readiness-check.js` (reusing the exact same
function, not a duplicated regex that could drift). Whichever managed
provider is chosen must issue/accept a TLS-terminated connection
string satisfying one of those three modes — this is a hard requirement,
not a recommendation.

## 3. Connection pooling and `max_connections` sizing

Each process that calls `PrismaService.onModuleInit()` (`$connect()`)
opens its own connection pool via `@prisma/client`'s built-in pooling
(default pool size: `num_physical_cpus * 2 + 1`, overridable via
`DATABASE_URL`'s `connection_limit` query parameter). With Phase 16's
API/worker split, a horizontally-scaled deployment now has **two
independently-scaling groups of processes** (N API replicas + M worker
replicas) each opening their own pool against the same database —
`max_connections` sizing must account for both, not just the API
replica count from before this phase.

Concretely, before scaling either replica count beyond 1:

- **Set an explicit `connection_limit`** on `DATABASE_URL` for both the
  API and worker deployments rather than relying on Prisma's CPU-derived
  default, which does not know it's sharing the database with another
  process group.
- **Size `max_connections`** (or the managed provider's equivalent —
  e.g. RDS's `max_connections` parameter-group setting) to comfortably
  exceed `(API replicas × API connection_limit) + (worker replicas ×
  worker connection_limit)`, with headroom for `psql`/admin tooling and
  the provider's own reserved superuser connections.
- **Prefer PgBouncer (transaction-pooling mode) once replica counts grow
  past a handful** — Prisma's own docs recommend this pattern for
  serverless/high-replica-count deployments; not configured anywhere in
  this repo, since no specific replica count or provider is chosen yet.
  `SerializableTransactionRunner`'s use of `SERIALIZABLE` isolation and
  explicit transactions is compatible with PgBouncer's transaction mode
  (session-level features like advisory locks or `LISTEN`/`NOTIFY`,
  which this codebase does not use, would not be).

**Status: READY FOR IMPLEMENTATION.** No real multi-replica load test
has been run against this schema/connection pattern.

## 4. Migration deployment process

- **Never** `prisma migrate dev` or `prisma migrate reset` against a
  shared database — both can drop/reset data on drift. `npm run
  prisma:migrate` (which wraps `prisma migrate dev`) now refuses to run
  at all when `APP_ENVIRONMENT=production` or `NODE_ENV=production`
  (`scripts/guard-destructive-migration.js`, Phase 16) — but this only
  protects the npm-script path; direct `npx prisma migrate dev` calls
  bypass it. The real safeguard is that the credential used for
  day-to-day migrations should never be handed to a developer's local
  shell against a shared database in the first place.

  **Known limitation, stated explicitly (Phase 16 review finding M3):**
  `guard-destructive-migration.js` checks the *names* `APP_ENVIRONMENT`/
  `NODE_ENV`, never the actual `DATABASE_URL` value. An operator whose
  shell has `DATABASE_URL` pointed at a real production database, but
  who has left `APP_ENVIRONMENT` unset or at its `sandbox` default (a
  plausible mistake — e.g. an incompletely-updated `.env`, or a copied
  shell session), is **not** blocked by this guard from running
  `prisma migrate dev` against that production database through the
  guarded npm script. This is a deliberate scope limitation, not an
  oversight the guard silently fails to mention: a connection-string-
  aware check would need to pattern-match hostnames/ports against a
  list of "known production" values that has to be kept in sync by
  hand and would itself be trivially wrong the moment infrastructure
  changes — a heuristic that can be silently stale is arguably worse
  than an honestly-narrow one. Until a real production Postgres
  provider is chosen (§5), the only substitute for this gap is
  operational discipline: the credential used for `prisma migrate dev`
  in any developer's local `DATABASE_URL` must never be a credential
  that can also reach a real production database — see the paragraph
  above.
- **Always** `npm run prisma:migrate:deploy` (`prisma migrate deploy`)
  against staging/production — applies only pending migrations from
  `prisma/migrations`, never resets, never prompts.
- **Run migrations as a separate, single-instance step before rolling
  out a new image** — never inside the container's own startup command.
  Both `apps/api/Dockerfile` targets' `CMD` deliberately never run
  `prisma migrate deploy` (see the Dockerfile's own comment) — running
  it from every replica's startup would race N replicas against the
  same migration.
- **CI validates the schema, and reports drift** — `.github/workflows/ci.yml`'s
  `prisma-migration-validation` job runs `prisma validate` (schema
  syntax — a hard gate) and separately reports
  `prisma migrate diff --from-migrations ... --to-schema-datamodel ...`
  against a throwaway Postgres service container as an informational,
  non-blocking step. It's non-blocking deliberately: run for real
  against this repo's actual migration history, it reports several
  FK/index declaration-ORDER differences across migrations that are
  cosmetic, not functional (Prisma's diff engine is sensitive to which
  migration re-declares a constraint, not just the resulting schema) —
  gating a merge on `--exit-code` here would make the check
  permanently, uninformatively red. "Migrations actually apply cleanly
  from a fresh database" — the property that matters for deployability —
  is already proven for real by the `ci` job's own integration-test
  suite on every run (its `global-setup.js` runs the exact same `prisma
  migrate deploy` against a fresh `embedded-postgres` instance), so this
  job doesn't duplicate that.

## 5. What is explicitly NOT decided here

Per this phase's own instructions, not fabricated:

1. **Which managed provider or self-hosted HA setup** (AWS RDS, GCP
   Cloud SQL, a self-hosted `pgBackRest`-managed box, ...) — determines
   what "automated backups"/PITR actually mean operationally. Unchanged
   from `docs/database-backup-recovery.md` §7's own item 1.
2. **WAL archiving / continuous backup** for true point-in-time recovery
   — not configured anywhere; `docs/database-backup-recovery.md` §3
   covers the current `pg_dump`-only posture in full.
3. **Explicit RPO/RTO targets** — still TBD (`docs/database-backup-recovery.md`
   §4), a business decision this document does not make on anyone's
   behalf.
4. **Read replicas** — nothing in this codebase currently reads from a
   replica; all Prisma calls go through the single `DATABASE_URL`. Not
   needed at current scale, not implemented speculatively.

**Do not deploy to production with real funds until §5's items are
explicitly decided** — this is the same standing warning
`docs/database-backup-recovery.md` §4 already makes, restated here
because it applies to this document's connection-pooling/HA guidance
too.
