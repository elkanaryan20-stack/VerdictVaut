# AWS Disaster Recovery — Phase 25

**Status: DESIGNED, NOT PROVISIONED.** No RDS instance exists. This
document translates `docs/production-database-readiness.md` (Phase
22's provider-neutral RPO/RTO targets, backup contract, HA assessment)
and `docs/disaster-recovery-runbooks.md` (Phase 22's runbooks A–M) into
AWS-specific terms. It does not re-derive targets or re-litigate the
HA gap Phase 22 already found — both remain authoritative, cited, not
duplicated.

## 2. RPO / RTO — restated from Phase 22, not changed

| | Proposed target (Phase 22, unchanged) | What AWS RDS Multi-AZ + PITR is expected to deliver |
|---|---|---|
| RPO | ≤ 5 minutes | RDS's continuous transaction-log upload (§1) makes a ≤5min RPO plausible for the PITR case; Multi-AZ's synchronous standby means a **failover** event (not a restore) has near-zero data loss for already-committed transactions — the two mechanisms cover different failure modes (§4 below) |
| RTO | ≤ 60 minutes | Not measured — restoring a PITR snapshot at real production data volume has never been tested against any real provider in any session (`docs/production-database-readiness.md` §12, unchanged); Multi-AZ failover itself is typically on the order of 60–120 seconds (AWS's own general guidance, not independently re-verified against current docs this specific session — flagged as unverified rather than asserted as fact) |

**These remain proposed targets requiring business sign-off, unchanged
from Phase 22.** This document does not accept them on anyone's
behalf.

## 3. Snapshot strategy

- **Automated daily snapshot** (RDS's standard automated-backup
  mechanism, §1) + continuous transaction-log upload for PITR within
  the retention window.
- **Manual snapshots before every production migration** — extends
  Phase 22's "run `infra/backup.sh` before every `prisma migrate
  deploy`" rule (`docs/production-database-readiness.md` §8, unchanged)
  to its AWS-native equivalent: an on-demand RDS snapshot immediately
  before running `prisma migrate deploy` against production. Unlike
  automated backups, a manual snapshot is retained until explicitly
  deleted — useful as a named, easy-to-find restore point tied to a
  specific migration.
- **Cross-region snapshot copy** — not designed this phase (§5 below,
  DR-region strategy is a distinct, larger decision); noted as the
  mechanism that would eventually support a real DR-region restore if
  that's ever pursued.

## 5. Disaster recovery region strategy

**Not designed as an active commitment this phase** — a genuine
cross-region DR strategy is a materially larger scope (replication
lag, a distinct RTO/RPO analysis, cost) than "pick a second region,"
consistent with `docs/production-database-readiness.md` §10's own
"regional DR / cross-region replica" row, which already flagged this
as a separate decision from single-region Multi-AZ.

What is documented here, without committing to it:

- **If pursued**: an RDS cross-region **read replica**, promotable to
  a standalone primary during a genuine regional outage, is AWS's
  standard mechanism — requires choosing a second region (a decision
  layered on top of, not resolved by, the primary-region choice in
  `docs/aws-production-architecture.md` §10) and accepting asynchronous
  replication lag as that replica's own RPO characteristic (distinct
  from, and looser than, the single-region Multi-AZ RPO in §2 above).
- **Application-layer implication**: this codebase is a
  single-primary-writer application by construction
  (`docs/production-database-readiness.md` §10, unchanged) — a
  cross-region promotion event is a manual, human-directed failover
  (update `DATABASE_URL` secrets, redeploy), not an automatic one; no
  automatic cross-region failover is designed or recommended.
- **Not selected, not costed, not scheduled.**

## 6. Migration procedure — aligned with existing runbooks, unchanged

`prisma migrate deploy` remains the only production migration
command, run as a single separate step (never inside container
startup — both Dockerfiles re-confirmed this session, unchanged),
preceded by a manual RDS snapshot (§3). Rollback follows
`docs/production-deployment-plan.md` §7 and
`docs/disaster-recovery-runbooks.md` runbook L — a bad migration is
fixed by a new forward migration or, if data is already lost, a real
disaster-recovery restore (§4) — **never an automatic destructive
rollback**, restated as a hard requirement from this phase's brief and
already the existing policy.
